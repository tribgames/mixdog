# Browser Use 입력 격리 진단

실제 Electron과 프로덕션 Browser Use 브리지를 사용합니다. 설치된 Mixdog를
종료하거나 재시작하지 않으며, 테스트용 프로필과 숨겨진 창을 생성합니다.

```powershell
node apps/desktop/scripts/run-browser-input-isolation.mjs
```

제품의 독립 페이지 경로와 실제 BrowserPane·preload·IPC 연결을 검사합니다.
별도 세션 입력 보존, 직접 클릭·한글 입력, 비활성 패널 실행, 숨긴 문서의 화면
폴링 중단, 오래된 문서·다른 세션 입력 거부, 페이지 재생성 시 로그인 저장소 유지,
화면 캡처 시간을 확인합니다.

## 확인된 현상

- 브라우저 `press`가 별도 세션의 컴포저에 전달되어 선택한 글을 교체합니다.
- `type`의 전체 선택·삭제·문자 삽입이 컴포저의 기존 글을 덮어씁니다.
- 브라우저 클릭이 컴포저를 흐리게 하고 내장 페이지로 포커스를 옮깁니다.
- 화면 밖에 보관된 페이지에서도 재현됩니다.

페이지 활성 에뮬레이션만으로는 내장 페이지의 입력 경로가 격리되지 않았습니다.
WebContents 전용 키보드 API로 바꾸는 부분 실험은 일반 입력 간섭을 막았지만,
클릭 포커스 이동은 남았고 cross-origin iframe 문자 삽입이 멈췄습니다.
따라서 해당 부분 패치는 제품 코드에 남기지 않았습니다.

독립 페이지와 활성 에뮬레이션을 사용하는 대조에서는 두 세션의 각 10개 항목,
총 20개 항목을 통과했습니다. 클릭·입력·Tab·탐색·iframe 입력 중에도 컴포저의
문자·선택 범위·방향·포커스 이벤트가 유지됐고, 한글 조합을 이어서 완료했습니다.
자동화 대상 필드에도 의도한 문자가 들어갔는지 함께 확인합니다.

이 결과는 숨겨진 테스트 창에서의 Electron 입력 경로 검증입니다.
설치 앱에서 실제 하드웨어 키보드로 동시에 입력하는 종단 검증을 대신하지 않습니다.

## 레퍼런스 대조

로컬 `C:\Project\refs`의 Playwright, agent-browser, browser-harness를 먼저
확인했습니다. Playwright는 페이지 단위 CDP 클라이언트와
`Emulation.setFocusEmulationEnabled`를 사용합니다. 다른 두 구현도 대상
페이지/세션의 CDP 입력을 사용하지만, Mixdog의 Electron 내장 `webview`가
컴포저와 포커스 경로를 공유하는 조건까지 보장하는 근거는 아니었습니다.
레퍼런스 코드는 복사하지 않았습니다.

## 구현 구조

기본 페이지와 지원 탭 모두 같은 영구 로그인 partition의 숨겨진 비활성 창에서
실행합니다. 기본 페이지는 패널을 숨겨도 유지하고 세션을 삭제할 때 해제합니다.
앱의 브라우저 패널은 화면을 받고, 로컬 사용자 입력은 세션·문서 토큰에 묶어
직렬 전달합니다. 화면 픽셀과 CSS 좌표를 분리해 확대 및 기기 해상도에도 대응합니다.
자동화 및 모바일 원격 조작의 기존 안전 규칙은 별도로 유지합니다.
